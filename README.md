## 2. Сценарио бүрээс SLO гаргах

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / Нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 50 мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | `/pay` error rate | < 8% (0.08) | 20 VU, 1 мин |
| Availability | Бүх хүсэлтийн амжилтын хувь (`checks`) | ≥ 90% (0.90) | 2 мин, 10с зогсолт орсон |
| Performance (Extra) | `/report` latency | p95 < 450 мс | 20 VU, 1 мин |

1. **Performance (`/cart/add`):** Локал машин дээр 1-5 мс хариулдаг ч 20 VU ачаалалтай үед сүлжээний болон процессорын саатал гарахаас сэргийлж p95 < 50ms босго тогтоов.
2. **Reliability (`/pay`):** Серверийн кодод `Math.random() < 0.05` буюу ~5%-ийн алдаа суулгасан тул санамсаргүй хэлбэлзлийг тооцон 8%-иас бага байх босго сонгов.
3. **Availability & Error Budget:** 2 минутын (120 секунд) цонход 90% availability гэдэг нь **12 секундээр тооцсон Error Budget** өгч байна. Серверийг 10 секунд зогсооход энэ цагийн budget-д багтана.
4. **Цагийн ба Хүсэлтийн budget-ийн зөрүү:** k6-ийн `checks` нь цагаар биш **ХҮСЭЛТИЙН тоогоор** тооцдог. Сервер унасан үед хүсэлт агшин зуур (Connection Refused / 0ms) буцдаг тул сааталтай (200-400ms) хэвийн секундээс илүү олон хүсэлт 1 секундэд амжиж унадаг. Тиймээс хүсэлтээр тооцсон алдааны хувь цагаар тооцсон 10 секундийн (8.3%) харьцаанаас өөр гардаг.


## 3. Chaos туршилт ба Ажиглалтын Дүгнэлт (Алхам 5)

### 1. Бодит Availability ба Error Budget-ийн хэтрэлт:
- **Үр дүн:** Availability threshold (`checks > 0.90`) **FAIL** болсон.
- **Дүгнэлт:** 2 минутын (120с) хугацаанд 90% availability гэдэг нь цаг хугацааны хувьд **12 секундийн Error Budget** өгдөг. Бид 10 орчим секунд серверийг зогсоосон тул цагаар бодвол budget-даа багтахаар байсан ч **хүсэлтийн тоогоор тооцоход budget хэтэрсэн**.

### 2. Цагийн budget ба Хүсэлтийн budget яагаад өөр гарсан бэ?
- **Шалтгаан:** k6 хэрэгслийн `checks` хэмжүүр нь **ЦАГИЙН биш ХҮСЭЛТИЙН хувиар** бодогддог. 
- Сервер хэвийн ажиллаж байх үед `/report` endpoint нь 200–400 мс хүлээж байж хариу буцаадаг тул 1 секундэд хязгаартай цөөн хүсэлт боловсруулдаг. 
- Гэтэл сервер унасан 10 секундэд хүсэлтүүд серверээс хүлээлгүйгээр агшин зуур **`Connection Refused` (0 мс)** зааж буцаж байсан тул сааталгүйгээр 1 секундэд хэвийн үеэс **3–5 дахин олон хүсэлт "идсэн"**. Тиймээс унасан хүсэлтийн эзлэх хувь огцом өсөж, 90%-ийн босгыг давж унагасан.

### 3. Reliability threshold (`/pay`) яагаад зэрэг FAIL болсон бэ?
- Сервер унахад `/pay` руу очсон бүх хүсэлт сүлжээний түвшинд тасарсан. Сервер бүхэлдээ унах нь Availability-г унагаахаас гадна тухайн функцийн ажиллагааг (Reliability) давхар зогсоодог тул нэг эвдрэл хоёр SLO-г зэрэг FAIL болгож байна.

### 4. Availability ба Reliability SLI-г тусгаарлах арга:
- Серверээс ямар нэг HTTP хариу (статус код) ирж байгаа хүсэлтүүдийг зөвхөн Reliability SLI-д тооцож, сервертэй огт холбогдож чадахгүй байгаа сүлжээний тасралт/алдааг (Connection Refused) тусад нь зөвхөн Availability SLI-д тооцох логикоор тусгаарлана.
